# 任務優先級支援設計

## Context

TimeScheduler 目前使用簡單的任務隊列，任務按加入順序執行。為了支援優先級，需要修改任務儲存和執行邏輯，使用優先隊列（priority queue）或排序列表來管理任務。

現有架構：
- `Scheduler` 維護 `_tasks` 字典（task_id -> Task）
- `Scheduler.run()` 迴圈檢查所有任務的 `should_run()`
- 無優先級概念，所有任務平等

## Goals / Non-Goals

**Goals:**
- 支援三個優先級等級：high, medium, low
- 高優先級任務優先執行
- 保持現有 API 的向後相容性
- 最小化效能影響

**Non-Goals:**
- 動態優先級調整（任務執行中改變優先級）
- 複雜的優先級調度演算法（如公平排程）
- 優先級與其他參數（如延遲）的複雜互動

## Decisions

### 優先級表示
使用字串枚舉：`"high"`, `"medium"`, `"low"`
- 理由：直觀易懂，易於序列化
- 替代方案：數值（1,2,3）被否決，因為不易讀

### 任務排序邏輯
在 `Scheduler.run()` 中，按優先級排序任務列表：
- high > medium > low
- 同優先級按加入順序（FIFO）
- 理由：簡單實現，符合大多數使用場景
- 替代方案：使用 heapq 優先隊列，但會增加複雜度

### 預設優先級
預設為 `"medium"`
- 理由：保持向後相容，新舊任務都屬於中等優先級

## Risks / Trade-offs

- **效能影響**：每次檢查時需要排序任務列表 → 對於大量任務（>1000）可能有效能問題。緩解：可考慮快取排序結果或使用優先隊列。
- **向後相容**：新參數預設值確保舊代碼正常運行 → 無問題。
- **API 複雜度**：增加參數使 API 更複雜 → 通過清晰文檔和範例緩解。
